# persian-rtl

پلاگینی برای Claude Code که هر بخشی از پیام‌های کاربر و دستیار، خروجی دستورهای `/` و فراخوانی و نتیجه‌ی ابزارها را که **دست‌کم یک نویسه‌ی فارسی** داشته باشد راست‌چین می‌کند و متن فارسی و انگلیسی مخلوط را در ترمینال درست، یعنی از راست به چپ، نشان می‌دهد. هر چه فارسی نداشته باشد چپ‌چین و با رندر خود Claude Code می‌ماند.

ترمینال‌هایی مثل Konsole خودشان bidi را درست انجام نمی‌دهند: جمله‌ی فارسی چپ‌چین می‌شود، نقطه‌ی پایانی به ابتدای جمله می‌پرد و کلمات انگلیسی وسط جمله جابه‌جا می‌شوند. این پلاگین پیش از رسیدن متن به ترمینال، چیدمان را خودش محاسبه می‌کند.

> **وضعیت:** آزمایش‌شده در Konsole با Claude Code نسخه‌ی 2.1.289. در ترمینال‌های دیگر ممکن است نتیجه فرق کند (بخش «محدودیت‌ها» را ببینید).

## نیازمندی‌ها

- **Claude Code** با پشتیبانی از پلاگین‌های «mod» (هوک‌های تابعی و رویداد `ui.render`)؛ آزمایش‌شده با نسخه‌ی 2.1.289.
- **ترمینال:** آزمایش‌شده فقط در Konsole؛ در ترمینال دیگر با `tools/bidi-oracle/calibrate.txt` رفتارش را بسنجید.
- **فونت هم‌عرض** با حروف فارسی (برای نمونه Vazir Code)؛ بخش «محدودیت‌ها».
- ابزارهای `tools/bidi-oracle/` فقط برای توسعه‌اند و به `bun` و `python3` و `libicuuc` نیاز دارند.

## نصب

### نصب دائمی (بدون هیچ سوئیچی در اجراهای بعدی)

پلاگین یک بار نصب می‌شود و از آن به بعد در هر اجرای `claude` فعال است:

```sh
claude plugin marketplace add /مسیر/به/این/مخزن      # یا نشانی GitHub مخزن
claude plugin install persian-rtl@rtlclaudecode
```

اگر Claude Code از قبل باز است، داخل آن `/reload-plugins` را بزنید. برای خاموش کردن: `claude plugin disable persian-rtl`.

### اجرای موقت (فقط برای همان اجرا)

```sh
claude --plugin-dir /مسیر/به/این/مخزن
```

در این حالت باید هر بار این سوئیچ را بدهید.

## حذف

هر کدام از این‌ها را متناسب با روش نصبتان انجام دهید. بعد از آن `/reload-plugins` را بزنید یا Claude Code را دوباره باز کنید.

| وضعیت | دستور |
| --- | --- |
| فقط خاموش کردن، بدون حذف (بعداً با `claude plugin enable persian-rtl` برمی‌گردد) | `claude plugin disable persian-rtl` |
| حذف پلاگین نصب‌شده | `claude plugin uninstall persian-rtl` |
| حذف marketplace محلی (بعد از حذف پلاگین) | `claude plugin marketplace remove rtlclaudecode` |
| اجرای موقت با `--plugin-dir` | کاری لازم نیست؛ فقط دیگر آن سوئیچ را ندهید |

اگر پلاگین را با `--scope project` یا `--scope local` نصب کرده‌اید، دستور حذف را هم با همان `--scope` بزنید. حذف پلاگین به فایل‌های مخزن دست نمی‌زند؛ پوشه‌ی مخزن را اگر لازم نیست خودتان پاک کنید.

## خلاصه‌های `· summary` و گزینه‌ی «یادداشت‌های پیشرفت به انگلیسی»

Claude Code متنی را که مدل **بین دو فراخوانی ابزار** می‌نویسد نشان نمی‌دهد؛ به‌جایش خلاصه‌ای را نشان می‌دهد که سرور از آن می‌سازد، با پسوند `· summary`. این خلاصه به زبان همان متن است و با کامپوننتی کشیده می‌شود که پلاگین‌ها به آن دسترسی ندارند. پس خلاصه‌ی فارسی چپ‌به‌راست و بههم‌ریخته دیده می‌شود. ولی خلاصه‌ی متن انگلیسی همان‌جا درست خوانده می‌شود.

پلاگین برای همین یک بخش به پرامپت سیستم اضافه می‌کند (رویداد `prompt.compose`): وقتی کاربر به فارسی، عربی، عبری یا اردو می‌نویسد، متنی را که بعد از آن ابزاری می‌آید به **انگلیسی** و کوتاه بنویسد، و پاسخ نهایی را به زبان خود کاربر. این بخش **به‌طور پیش‌فرض روشن** است.

برای خاموش کردن (گزینه‌ی `englishProgressNotes` در مانیفست، از نوع بولین با پیش‌فرض `true`):

| روش | چطور |
| --- | --- |
| منوی تنظیمات | `/config` ← ردیف «Progress notes in English» |
| خط فرمان | `echo '{"englishProgressNotes":"false"}' \| claude plugin configure persian-rtl --values-stdin` |
| فایل تنظیمات | زیر `pluginConfigs` ← `persian-rtl` ← `englishProgressNotes` |

بعد از تغییر، پلاگین دوباره بار می‌شود (یا `/reload-plugins`). این تنظیم فقط روی **نوبت‌های بعدی** اثر دارد. محدودیت‌ها:
- **اولین پیام هر نوبت:** خلاصه نمی‌شود و متن واقعی نشان داده می‌شود. اگر به انگلیسی نوشته شود، چپ‌چین (و درست) دیده می‌شود.
- **تضمین نیست:** خلاصه را سرور می‌سازد؛ مدل ممکن است گاهی دستور را رعایت نکند، و حتی با متن انگلیسی ممکن است خلاصه عبارتی فارسی داشته باشد.
- **تغییر رفتار مدل:** این گزینه نمایش را عوض نمی‌کند، بلکه چیزی را که مدل می‌نویسد.

## چه کاری می‌کند

| ورودی | نتیجه |
| --- | --- |
| پاسخ دستیار و پیام کاربر | هر بند که دست‌کم یک نویسه‌ی فارسی داشته باشد کنار راست و راست‌به‌چپ چیده می‌شود؛ هر بند بدون فارسی چپ‌چین می‌ماند. پیامی که اصلاً فارسی نداشته باشد کاملاً با رندر خود Claude Code (با `●` و مارک‌داون) نمایش داده می‌شود |
| نقطه، ویرگول فارسی، گیومه، پرانتز | در سمت درست جمله می‌نشینند (پرانتز و «» آینه می‌شوند) |
| کلمات انگلیسی و `code` میان جمله‌ی فارسی | ترتیب خواندن درست می‌ماند |
| لیست نقطه‌ای و شماره‌دار، نقل‌قول `>`، عنوان `#` | نشانگر در لبه‌ی راست است و خط‌های بعدی زیر متن آویزان می‌شوند |
| `**bold**`، `*italic*`، `` `code` `` | پررنگ، مایل و فیروزه‌ای رندر می‌شوند |
| بلوک کد | بدون تغییر و چپ‌چین (با رندر خود Claude Code) |
| جدول مارک‌داون که دست‌کم یک نویسه‌ی فارسی داشته باشد | با نویسه‌های ترسیم قاب کشیده می‌شود: ستون اول سمت **راست**، هر سلول مثل یک بند جدا راست‌به‌چپ چیده می‌شود و در ستونِ دارای فارسی به راست تراز است، و کل جدول در لبه‌ی راست می‌نشیند. جدولی که فارسی ندارد را موتور مثل همیشه می‌کشد |
| خروجی دستورهای `/` (`CommandOutput`) و خط‌های وضعیت زیر لوگو (`InfoNotice`) | اگر دست‌کم یک نویسه‌ی فارسی داشته باشند، مثل پیام‌ها راست‌چین می‌شوند |
| ردیف فراخوانی ابزار (`ToolUse`، مثل `Bash(...)`) | اگر ورودی ابزار دست‌کم یک نویسه‌ی فارسی داشته باشد، یک خط `ابزار(آرگومان اصلی)` با `●` در لبه‌ی راست جای ردیف اصلی می‌نشیند |
| نتیجه‌ی ابزار (`ToolResult`): Bash، Read، Grep و هر ابزاری که متنش در `stdout`، `content`، `file.content`، `text`، `result` یا `output` باشد | اگر دست‌کم یک نویسه‌ی فارسی داشته باشد، خط‌به‌خط راست‌چین می‌شود (حداکثر ۶۰ خط، بدون تجزیه‌ی مارک‌داون، stderr قرمز) |

## محدودیت‌ها

- **مارک‌داون ساده‌شده:** فقط `**bold**`، `*italic*`، `` `code` ``، عنوان، لیست، نقل‌قول و جدول پشتیبانی می‌شوند. لینک‌ها فقط به متن برچسبشان تبدیل می‌شوند. بلوک کد با رندر خود Claude Code نمایش داده می‌شود.
- **جدول:** نشانگر تراز مارک‌داون (`:---:`) نادیده گرفته می‌شود و تراز را خود پلاگین تعیین می‌کند. اگر جدول از عرض ترمینال پهن‌تر باشد، ستون‌ها تا حداقل ۶ خانه کوتاه و متن سلول‌ها در چند خط شکسته می‌شود؛ پایین‌تر از آن جدول از عرض بیرون می‌زند. سلولِ دارای نماد شکننده (`●`، بند ۷ بالا) هم مثل متن معمولی چیده می‌شود. جدول فقط برای متن مارک‌داونِ پیام و `CommandOutput` کشیده می‌شود، نه برای نتیجه‌ی ابزارها.
- **نشانگرهای ابتدای پیام:** `●` ابتدای پاسخ و `❯` پیام کاربر برای پیام‌های راست‌چین‌شده دیده نمی‌شود.
- **خلاصه‌های `· summary` (پیام‌های میانی):** ردیف‌هایی که با `●` شروع می‌شوند و در انتها `· summary` دارند، خلاصه‌ی سمت سرور از متنِ بین فراخوانی‌های ابزار هستند (در کد Claude Code «narration» نام دارند). این‌ها با یک کامپوننت داخلی کشیده می‌شوند که برخلاف `AssistantMessage` از سامانه‌ی هوک عبور نمی‌کند، پس هیچ پلاگینی نمی‌تواند آن‌ها را راست‌چین کند. راه‌حل پلاگین این است که خلاصه‌ها انگلیسی باشند (بخش بالا). تنظیم `showThinkingSummaries: false` در `settings.json` اثری ندارد: در نشست تعاملی با نبودنش یکی است و فقط `true` چیزی را عوض می‌کند. گزینه‌ی خط فرمان `--thinking-display` را آزمایش نکرده‌ام.
- **خروجی ابزارهای ساختاریافته:** نتیجه‌ی ابزارهایی که متنشان در یکی از فیلدهای بالا نیست (مثل diff ویرایش `Edit` و `Write`) و ردیف‌های چندبخشی (`ToolGroup` مثل `Ran 2 shell commands`) را موتور خودش می‌کشد و راست‌چین نمی‌شوند.
- **دیالوگ پرسش (`AskUserQuestion`):** راست‌چین نمی‌شود، چون تعاملی است و جایگزین کردنش گزینه‌های انتخابی را از کار می‌اندازد.
- **کادر ورودی (جایی که تایپ می‌کنید):** راست‌چین نمی‌شود. پلاگین‌ها فقط می‌توانند متن پیش‌نویس را بخوانند و تغییر بدهند یا روی نویسه‌هایش رنگ بزنند، نه جای آن را. چیدمان آن کار خود Claude Code است. بعد از ارسال، پیام در `UserMessage` راست‌چین می‌شود.
- **نوار پایین و خطوط وضعیت** (`Spinner`، `TurnDuration`، `PromptHint`، `SessionMode`): این‌ها متن ثابت انگلیسی هستند و چیزی برای راست‌چین کردن ندارند.
- **فونت:** پلاگین فونت ترمینال را تغییر نمی‌دهد و نمی‌تواند؛ فونت را خود ترمینال انتخاب می‌کند (در Konsole: Settings ← Edit Current Profile ← Appearance ← Font). ترمینال به فونت **هم‌عرض** نیاز دارد، پس فونت‌های متناسب مثل Vazirmatn مناسب نیستند و حروف لاتین و فاصله‌ها را بههم می‌ریزند. فونت هم‌عرضِ فارسی [Vazir Code](https://github.com/rastikerdar/vazir-code-font) این مشکل را ندارد: از میان نسخه‌هایش `Vazir Code Hack` حروف لاتین فونت Hack را دارد و برای کد مناسب است، پسوند `FD` ارقام فارسی را به‌جای لاتین می‌گذارد، `WOL` لیگاچر را حذف می‌کند و `Extra Height` فاصله‌ی خطوط را بیشتر می‌کند. چیدمان این پلاگین هر نویسه را یک خانه حساب می‌کند و با فونت هم‌عرض سازگار است. تغییر فونت فقط ظاهر را عوض می‌کند و ترتیب راست‌به‌چپ را که این پلاگین حساب می‌کند تغییر نمی‌دهد.
- **عرض خط:** از عرض ترمینال منهای ۶ ستون استفاده می‌شود. اگر ترمینال عرضش را اعلام نکند ۸۰ ستون فرض می‌شود.
- **نویسه‌ی خالی U+2800:** جلوی کلمه‌ی لاتینِ شروع‌شده با رقم (مثل `6.png`)، جلوی شماره‌ی لیست و جلوی جزیره‌ی پرانتز گذاشته می‌شود. اگر قلم ترمینال این نویسه را خالی نکشد، یک خانه‌ی غیرخالی دیده می‌شود. وقتی پرانتز بدون فاصله به کلمه‌ی فارسی قبلش چسبیده باشد (`کلمه(توضیح)`) یا بعد از `؛` و `؟` بیاید، همین یک خانه‌ی خالی بین آن‌ها می‌افتد.
- **ترمینال‌های دیگر:** چیدمان برای رفتار Konsole تنظیم شده است (bidi روی ردیف با جهت پایه‌ی چپ‌به‌راست که در نمادهای `U+2500`–`U+25FF` قطع می‌شود). در ترمینال‌هایی که bidi را انجام نمی‌دهند یا به شکل دیگری انجام می‌دهند ممکن است ترتیب کلمات برعکس دیده شود.
- **بند بدون فارسی:** در پیامی که هم بند فارسی دارد و هم بند انگلیسی، بند انگلیسی چپ‌چین و با ترتیب و نقطه‌ی خودش نمایش داده می‌شود. پیامی که یک نویسه‌ی فارسی هم نداشته باشد اصلاً دست‌کاری نمی‌شود.

## چرا این‌طور کار می‌کند

آزمایش در Konsole (که الگوریتم bidi کتابخانه‌ی ICU را به کار می‌برد) این‌ها را نشان داد:

1. Konsole bidi را روی **کل ردیف** (جز در نمادهای بند ۷) با جهت پایه‌ی **چپ‌به‌راست** اجرا می‌کند. پس هر گروه حروف فارسی را خودش وارونه می‌چیند، ولی نقطه‌ی پایان جمله را سمت راست می‌گذارد.
2. نویسه‌های کنترلی بدون عرض (`RLM`، `LRM`) به خانه‌ی قبلی می‌چسبند و نادیده گرفته می‌شوند. `RLE`، `RLI`، `PDF`، `PDI` و `ALM` به شکل `�` کشیده می‌شوند. پس راه «جهت را با نویسه‌ی کنترلی اعلام کن» کار نمی‌کند.
3. رقم بعد از حروف فارسی «عدد عربی» می‌شود و به گروه فارسی می‌چسبد؛ رقمِ ابتدای یک گروه فارسی که قبلش حرف لاتین یا ابتدای ردیف باشد، «لاتین» حساب می‌شود و به لبه‌ی چپ گروه می‌رود. (اگر قبلش یک حرف راست‌به‌چپ مثل «؛» یا «؟» باشد درست می‌ماند.)
4. Konsole ترتیب جای حروف گروه فارسی را برمی‌گرداند ولی گلیف براکت‌ها را **آینه نمی‌کند**؛ پس `(۱۲۳)` درون جمله‌ی فارسی به شکل `)۱۲۳(` دیده می‌شود.
5. ICU یک `(` را با نزدیک‌ترین `)` بعدی **جفت** می‌کند (قاعده‌ی N0). اگر براکت‌ها را یکی‌یکی جابه‌جا کنیم (`(` ↔ `)`)، بین گروه‌های مجاور جفت‌های ساختگی ساخته می‌شود و اگر کلمه‌ی لاتین میانشان باشد، ICU آن‌ها را چپ‌به‌راست می‌کند و گروه فارسی را وسط می‌شکند.
6. `؛` و `؟` برای bidi حرف راست‌به‌چپ قوی هستند و `،` و `.` خنثی. رفتارشان در لبه‌ی گروه فرق می‌کند.
7. Konsole ردیف را در بعضی نویسه‌ها **می‌شکند** و هر طرف را جدا و چپ‌به‌راست می‌چیند، و دو طرف به همان ترتیبی که نوشته شده‌اند پشت هم می‌آیند (پس متن دو طرفِ یک `●` راست‌به‌چپ خوانده نمی‌شود). با `tools/bidi-oracle/calibrate.txt` (یک خط `اول دوم X سوم چهارم` برای هر نماد) روی صفحه اندازه گرفتم: `● ○ ◆ ◇ ■ □ ▶` می‌شکنند و `• · → ← — – ❯ ★ ✓ … « » - / | * # ( ) . : ،` و رقم نمی‌شکنند. همه‌ی نمادهای شکننده در بلوک‌های «ترسیم قاب»، «بلوک‌ها» و «اشکال هندسی» (`U+2500` تا `U+25FF`) هستند که Konsole احتمالاً خودش می‌کشد. این برای فونت و نسخه‌ی شما اندازه‌گیری شده است؛ در ترمینال دیگر با همان فایل دوباره بسنجید.

بنابراین `hooks/bidi.ts` متن را این‌طور می‌چیند:

1. متن به کلمه‌ها شکسته می‌شود و هر نویسه استایل خودش (`plain`، `bold`، `italic`، `code`) را دارد. استایل روی ترتیب اثر ندارد.
2. کلمه‌ها در ردیف‌هایی به عرض ترمینال شکسته می‌شوند. موتور خودش خطی نمی‌شکند.
3. جهت هر **بند** جدا تعیین می‌شود: اگر دست‌کم یک کلمه‌ی فارسی داشته باشد، راست‌به‌چپ و کنار راست چیده می‌شود (حتی اگر با کلمه‌ی انگلیسی شروع شود)، وگرنه بند چپ‌چین می‌ماند و ترتیب و نقطه‌ی خودش را نگه می‌دارد.
4. در هر ردیف راست‌به‌چپ، کلمه‌های پشت‌سرهم با زبان یکسان یک «گروه» می‌شوند. فارسی یعنی دست‌کم یک حرف یا رقم فارسی. لاتین یعنی بقیه‌ی کلمه‌های حرف‌دار. کلمه‌ی بدون حرف (مثل `-` یا عدد) به گروه قبلی می‌چسبد. کلمه‌ی مخلوط (`mod‌ها`، `remote‌ای`، `config‌شده`، `کلاس‌Konsole`) در مرز زبان به تکه‌هایی بریده می‌شود که بدون فاصله به هم می‌چسبند و هر تکه در گروه خودش می‌آید؛ وگرنه حروف لاتینِ وسط آن گروه فارسی را برای ICU می‌شکند و ترتیب بخش‌ها چپ‌به‌راست می‌ماند. هر دنباله‌ی `` `code` `` یک واحد چپ‌به‌راست و دست‌نخورده است (مسیر، شماره‌ی نسخه، ارقام فارسی داخلش)، مگر فقط متن فارسی باشد یا هیچ حرف و رقمی نداشته باشد (مثل `` `●` ``).
5. گروه‌ها **برعکس** پشت هم قرار می‌گیرند. داخل هر گروه ترتیب منطقی می‌ماند و Konsole حروف گروه فارسی را خودش وارونه می‌کند.
6. علامت خنثی در لبه‌ی گروه (`.` `،` `:` `!` `)` ...) به طرف دیگر گروه می‌رود و براکت‌ها آینه می‌شوند. همین برای **کلمه‌ای که فقط نماد باشد** (`●` `·` `→` `—` `◆`) در لبه‌ی گروه هم هست، حتی اگر داخل `` `code` `` باشد؛ تکه‌ای که همه‌ی کلماتش نماد باشد به ترتیب نمایش داده می‌شود. `؛` و `؟` در جای خود می‌مانند، چون ICU خودش آن‌ها را سمت چپ می‌برد. «لبه‌ی کلمه» یعنی نویسه‌های نگارشی و هر نماد یا علامت **غیر ASCII** (`●` `→` `—` `·`)؛ نمادهای ASCII (`/` `~` `#` `@` `-`) بخشی از همان کلمه‌اند (مسیر، گزینه، برچسب) و نمی‌روند، و علامت‌های همراه عدد (`٪` `‰` `°` و ارزها) هم با عدد می‌مانند.
7. **جزیره:** پرانتز یا براکتی که داخل یک گروه فارسی باز و بسته شود یک «جزیره» است: یک جفت واقعی `(…)` که جلویش یک خانه‌ی خالیِ چپ‌به‌راست (U+2800) هست تا ICU آن را چپ‌به‌راست و سر جایش نگه دارد. محتوایش داخلش و با همین قواعد چیده می‌شود. علامت چسبیده به جزیره (`(…)،` یا `«(…)»`) همراه آن می‌رود.
8. براکتی که جفتش در گروه دیگری است و کنار لبه نیست، گروه را می‌شکند و خودش میان دو تکه می‌ایستد.
9. رقمِ ابتدای گروه فارسی بعد از گروه جا می‌گیرد و با همان نویسه‌ی خالی از آن جدا می‌شود.
10. نشانگر لیست به انتهای ردیف (لبه‌ی راست) می‌رود؛ در بند بدون فارسی در سمت چپ است.
11. هر ردیف در یک `Box` با `alignSelf="flex-end"` رندر می‌شود و استایل نویسه‌ها به `Text` تبدیل می‌شود.
12. **نماد شکننده** (`U+2500`–`U+25FF`، مثل `●`): ردیف در آن به تکه‌هایی بریده می‌شود، هر تکه مستقل راست‌به‌چپ چیده می‌شود (همان قواعد بالا، با لبه‌ی خودش) و تکه‌ها به ترتیب **معکوس** با نماد میانشان پشت هم می‌آیند. فاصله‌ی کنار نماد به یک نویسه‌ی خالی تبدیل می‌شود تا در ترمینال‌هایی که ردیف را نمی‌شکنند هم تکه‌ها با هم ادغام نشوند. نمادی که بین دو کلمه‌ی لاتین باشد در جمله‌ی چپ‌به‌راست است و بریده نمی‌شود. پرانتزی که دورِ یک نماد شکننده بسته شده با همان نویسه‌ی خالی از متن فارسی جدا می‌ماند.

## ساختار مخزن

```
.claude-plugin/plugin.json        مانیفست پلاگین
.claude-plugin/marketplace.json   مانیفست marketplace (برای نصب دائمی)
hooks/hooks.json                  ماژول‌های پلاگین را معرفی می‌کند
hooks/register.tsx                هوک ui.render برای AssistantMessage، UserMessage، CommandOutput، InfoNotice، ToolUse و ToolResult، رندر JSX
hooks/bidi.ts                     تجزیه‌ی مارک‌داون، شکستن خط و چیدمان راست‌به‌چپ (بدون وابستگی به UI)
hooks/progress-notes.ts           متن بخش پرامپتِ «یادداشت‌های پیشرفت به انگلیسی»
hooks/table.ts                    چیدمان جدول مارک‌داون برای خواننده‌ی راست‌به‌چپ (بدون وابستگی به UI)
hooks/register.test.ts, table.test.ts   آزمون‌ها
tools/bidi-oracle/                ابزار سنجش چیدمان با ICU و مدل Konsole (بخش «توسعه»)
tools/bidi-oracle/calibrate.txt   خط‌های آزمایش برای اندازه‌گیری رفتار یک ترمینال (`cat` کنید و ببینید)
tools/bidi-oracle/table.ts, .py   سنجش یک جدول، سلول به سلول، با حالت درست راست‌به‌چپ
```

## توسعه

```sh
claude plugin validate .          # اعتبارسنجی مانیفست و هوک‌ها
claude plugin test .              # اجرای آزمون‌ها
claude --plugin-dir .             # اجرای Claude Code با نسخه‌ی در حال ویرایش
```

- `hooks/bidi.ts` عمداً به API پلاگین وابسته نیست تا با `claude plugin test` آزمون شود. هر تغییری در قواعد چیدمان باید یک آزمون داشته باشد.
- **ابزار سنجش:** `tools/bidi-oracle/` نشان می‌دهد Konsole برای رشته‌ای که پلاگین می‌فرستد دقیقاً چه می‌کشد، بدون نیاز به اسکرین‌شات. با ICU سیستم، هر ردیف را با اجرای bidi چپ‌به‌راست و بدون آینه‌کردن گلیف (آنچه Konsole می‌کند) می‌کشد و با نمایش درست راست‌به‌چپ همان متن مقایسه می‌کند. به `bun`، `python3` و کتابخانه‌ی `libicuuc` نیاز دارد:

  ```sh
  bun tools/bidi-oracle/rows.ts متن.md 114 | python3 tools/bidi-oracle/icu.py   # مقایسه‌ی ردیف‌های یک متن
  python3 tools/bidi-oracle/fuzz.py 1 500 8                                     # جمله‌های تصادفی
  bun tools/bidi-oracle/table.ts جدول.md 80 > t.json && python3 tools/bidi-oracle/table.py t.json   # یک جدول
  ```

  اختلاف «فقط یک خانه‌ی خالی» همان نویسه‌ی U+2800 است که چیدمان لازم دارد. چند اختلاف «ترتیب» هم ساختگی‌اند، چون ابزار عبارت لاتین را کامل نگه می‌دارد و نمی‌تواند هر تقسیم‌بندی خواننده را حدس بزند. هر تغییر در قواعد چیدمان باید با این ابزار و با یک آزمون همراه باشد.
- نتیجه‌ی نهایی رنگ و قلم را فقط می‌شود در خود ترمینال دید. آزمون‌ها ترتیب رشته‌ی خروجی را بررسی می‌کنند، نه رنگ‌آمیزی ترمینال را.
